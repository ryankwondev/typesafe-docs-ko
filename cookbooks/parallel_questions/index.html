    Parallel questions¶

    GDPR Wikipedia 문서를 대상으로 질문 13개짜리 규제 브리핑을 실행하여, 모든 질문을 TypeSafe 호출 하나로 묶는 batching(일괄 전송)이 답은 그대로 두면서 비용을 12.2배 낮추고 속도를 11.8배 높인다는 점을 보여 줍니다.

    문서 하나가 있고 그 문서에 대한 질문이 N개 있습니다. 질문 N개를 모두 담은 요청 하나를 보낼 수도 있고, 질문을 하나씩 담은 요청 N개를 보낼 수도 있습니다. Jev에서는 어느 쪽이든 답이 같습니다. 각 질문은 문서를 기준으로 독립적으로 채점되므로, 요청에 다른 무엇이 들어 있는지에 따라 답이 달라지지 않습니다.

    이를 확인하기 위해 각 질문을 두 방식(N개를 모두 한 요청에, 그리고 요청당 질문 하나)으로 여러 번 묻고 실행 간 표준편차를 비교합니다. 표준편차는 반복할 때마다 답이 얼마나 움직이는지를 나타냅니다. batching은 의미 있는 노이즈를 더하지 않습니다. 답 13개 중 7개는 어느 방식에서든 5회 반복 내내 똑같이 나와 표준편차가 정확히 0.0이었고, 나머지도 두 전략 모두에서 최대 0.015밖에 움직이지 않았습니다.

    달라지는 것은 비용과 속도입니다. 모든 요청에서 문서가 대부분을 차지합니다. 질문을 하나씩 보내는 호출 N개는 문서 비용을 N번 내고 왕복도 N번 합니다. 묶어 보낸 호출은 한 번만 냅니다. 문서가 클수록 절감 폭은 N배에 가까워집니다.

    여기서 다루는 사례는 규제 브리핑입니다. 문서는 GDPR에 대한 Wikipedia 문서(\~54,000자)이고, 컴플라이언스 팀이 확인하고 싶은 항목은 13개입니다. Noul 질문 8개, Choice 질문 2개, Score 질문 3개입니다.

    두 방식으로 5번씩 묻기¶

    호출마다 질문 일부를 문서와 함께 보내고, 각 답을 추적 대상 숫자 하나로 줄입니다. 문서는 모든 호출에서 바이트 단위까지 동일합니다.

    두 batching 전략 모두 RUNS = 5번 실행합니다. 평균(두 방식이 일치하는가?)과 표준편차(batching이 노이즈를 더하는가?)를 비교하기에 충분한 횟수입니다. 호출은 parallel_questions_cache.json에 캐시됩니다. 실시간으로 실행하려면 DOWNLOAD_CACHE = False로 설정하고 이 파일을 삭제하세요.

    @json_cache
def ask(document_json: str, questions_json: str, run: int, model: str):
    """One TypeSafe call -> ({key: tracked metric}, input_tokens, output_tokens, latency_s);
    ``run`` only forces a distinct live call per repeat."""
    started = perf_counter()
    questions = json.loads(questions_json)
    response = client.system_one(
        state={"article": json.loads(document_json)},
        questions=questions,
        model=model,
    )
    values = {}
    for key, question in questions.items():
        answer = response.answers[key]
        if isinstance(answer, NoulAnswer):
            values[key] = answer.noul
        elif isinstance(answer, ChoiceAnswer):
            values[key] = max(answer.probabilities.values())
        else:
            values[key] = answer.score / (len(question["criteria"]) - 1)
    return (
        values,
        response.usage.input_tokens,
        response.usage.output_tokens,
        perf_counter() - started,
    )


def ask_keys(keys: tuple[str, ...], run: int):
    """Ask the questions named by ``keys``, sending their full text."""
    questions = {key: QUESTIONS[key].model_dump(mode="json", exclude_none=True) for key in keys}
    return ask(json.dumps(DOCUMENT), json.dumps(questions), run, model=TYPESAFE_MODEL)


def priced(result):
    """({key: metric}, in_tokens, out_tokens, latency) -> ({key: metric}, cost_usd, latency)."""
    values, input_tokens, output_tokens, latency = result
    return values, input_tokens / 1e6 * PRICE[0] + output_tokens / 1e6 * PRICE[1], latency


# 가격은 캐시에서 꺼낸 뒤에 계산하므로, 가격이 바뀌어도 새로 호출할 필요가 없습니다.
batched = [
    priced(ask_keys(tuple(QUESTIONS), run)) for run in range(RUNS)
]  # N개 전부를 호출 하나에, x RUNS
singles = [
    {key: priced(ask_keys((key,), run)) for key in QUESTIONS} for run in range(RUNS)
]  # N x 1, x RUNS

    batching은 답을 바꾸지 않습니다¶

    아래 표는 질문별로, 각 batching 전략에서 5회 실행하는 동안 추적한 숫자의 평균과 표준편차를 보여 줍니다. batched 열과 single 열 사이에서 평균이 달라지면 편향이고, 표준편차가 커지면 노이즈입니다.

    print(
    f"{'question':<22}{'metric':<18}{'batched mean':>13}{'single mean':>12}"
    f"{'batched std':>13}{'single std':>12}"
)
for key, question in QUESTIONS.items():
    batched_values = [values[key] for values, _cost, _latency in batched]
    single_values = [singles[run][key][0][key] for run in range(RUNS)]
    print(
        f"{key:<22}{METRIC[type(question)]:<18}{mean(batched_values):>13.3f}"
        f"{mean(single_values):>12.3f}{stdev(batched_values):>13.4f}{stdev(single_values):>12.4f}"
    )

    • 나머지 여섯 개에는 실행 간 샘플링 노이즈가 조금 있으며, 어느 전략에서든 최대 0.015입니다. 그중 다섯 개는 묶어 보낸 쪽의 표준편차가 약간 더 높은데, 차이는 최대 0.0045로 반복 한 번이 0.01 움직인 정도의 크기입니다. 묶어 보낸 쪽과 하나씩 보낸 쪽의 평균은 0.004 이내로 일치하므로, batching 때문에 답이 한쪽으로 치우치지는 않습니다.

    유일한 차이: 비용과 속도¶

    \~54,000자짜리 문서가 모든 요청의 대부분을 차지하므로 다음과 같은 차이가 생깁니다.

    • 비용: 질문을 하나씩 보내는 호출 13개는 문서를 13번 다시 보내고, 묶어 보낸 호출은 한 번만 보냅니다. 이 절감 효과는 호출을 어떤 방식으로 실행하든 그대로입니다.
    • 속도: 표는 단일 질문 호출 13개의 지연 시간을 합산한 것이므로, 호출을 차례로 하나씩 실행한다고 가정합니다. 동시에 실행하면 격차가 줄어들지만, 12.2배의 비용 격차는 그대로 남습니다.

    비용과 시간은 5회 실행의 평균입니다.

    batched_cost = mean(cost for _values, cost, _latency in batched)
batched_latency = mean(latency for _values, _cost, latency in batched)
singles_cost = mean(
    sum(singles[run][key][1] for key in QUESTIONS) for run in range(RUNS)
)
singles_latency = mean(
    sum(singles[run][key][2] for key in QUESTIONS) for run in range(RUNS)
)
print(f"{'batching':<24}{'calls':>6}{'cost':>12}{'total time':>12}")
print(
    f"{f'one call, all {N}':<24}{1:>6}{'$' + format(batched_cost, '.6f'):>12}{format(batched_latency, '.2f') + 's':>12}"
)
print(
    f"{f'{N} calls, one each':<24}{N:>6}{'$' + format(singles_cost, '.6f'):>12}{format(singles_latency, '.2f') + 's':>12}"
)
print(
    f"\nbatching: {singles_cost / batched_cost:.1f}x cheaper, {singles_latency / batched_latency:.1f}x faster"
)
